SECTION 1: INCIDENT SEVERITY LEVELS
====================================================================

All production incidents are classified into four severity levels:

SEV-1 (Critical)
- Definition: Complete service outage or data loss/corruption affecting ALL customers.
- Response Time: Page on-call SRE within 2 minutes.
- Resolution Target: Mitigation within 30 minutes; resolution within 2 hours.
- Communication: Status page update every 10 minutes. CEO and VP Eng notified immediately.
- Post-mortem: Required within 48 hours.

SEV-2 (High)
- Definition: Significant degradation (>20% error rate or >2x P99 latency) affecting many customers.
- Response Time: Page on-call SRE within 5 minutes.
- Resolution Target: Mitigation within 1 hour; resolution within 4 hours.
- Communication: Status page update every 30 minutes.
- Post-mortem: Required within 5 business days.

SEV-3 (Medium)
- Definition: Partial feature unavailability; workaround exists; limited customer impact.
- Response Time: Notify via Slack #incidents channel; on-call acknowledges within 15 minutes.
- Resolution Target: 1 business day.
- Communication: Internal Slack only unless customers explicitly affected.
- Post-mortem: Optional (encouraged for recurring issues).

SEV-4 (Low)
- Definition: Non-customer-facing issue; minor bug; single customer affected.
- Response Time: Ticket created within 1 hour; picked up in next sprint.
- Resolution Target: Next sprint.
- Communication: GitHub issue only.
- Post-mortem: Not required.

SECTION 3: COMMON RUNBOOKS
====================================================================

--- RUNBOOK: High Database CPU ---

Trigger: PostgreSQL CPU > 90% for 5 consecutive minutes (alert: DB_CPU_HIGH)

Steps:
1. Check pg_stat_activity for long-running queries:
   SELECT pid, now() - pg_stat_activity.query_start AS duration, query, state
   FROM pg_stat_activity
   WHERE (now() - pg_stat_activity.query_start) > interval '30 seconds';

2. Identify and cancel expensive queries if safe:
   SELECT pg_cancel_backend(<pid>);

3. Check for missing indexes using pg_stat_user_tables:
   SELECT relname, seq_scan, idx_scan FROM pg_stat_user_tables ORDER BY seq_scan DESC LIMIT 10;

4. If CPU remains high after query cancellation, check for lock contention:
   SELECT * FROM pg_locks WHERE NOT granted;

5. Escalate to DBA on-call if issue persists beyond 20 minutes.

--- RUNBOOK: Qdrant Vector Store Unavailable ---

Trigger: Health check to qdrant:6333/healthz returns non-200 for 2 consecutive minutes.

Steps:
1. SSH to qdrant-01 or qdrant-02 node.
2. Check container status: docker ps | grep qdrant
3. If container is down: docker start qdrant
4. Check logs: docker logs qdrant --tail=200
5. If disk full (common cause): df -h; clear old snapshots in /data/qdrant/snapshots/
6. Verify replication: curl http://qdrant-01:6333/cluster
7. If single node is degraded, reroute traffic to replica: update QDRANT_HOST env var in app config and redeploy.
8. File SEV-2 if both nodes are unavailable.

--- RUNBOOK: Record Ingestion Lag > 60 seconds ---

Trigger: Kafka consumer group lag > 100,000 records OR ingest latency P99 > 60s (alert: INGEST_LAG_HIGH)

Steps:
1. Check Kafka consumer group status:
   kafka-consumer-groups.sh --bootstrap-server kafka:9092 --describe --group acme-ingest

2. Check ingest worker health: kubectl get pods -n ingest | grep ingest-worker

3. Scale workers if healthy: kubectl scale deployment ingest-worker --replicas=20

4. If workers are crash-looping, check logs:
   kubectl logs -l app=ingest-worker --tail=100

5. Check for schema validation errors in logs (may indicate bad producer data).

6. If lag > 1,000,000 records, escalate to SEV-2.

--- RUNBOOK: SSL Certificate Expiry ---

Trigger: Certificate expiry within 14 days (alert: SSL_CERT_EXPIRY_14D)

Steps:
1. Verify expiry: echo | openssl s_client -connect api.acmecorp.example.com:443 2>/dev/null | openssl x509 -noout -dates
2. Certificates are managed via Let's Encrypt / Certbot on the API gateway.
3. Manual renewal: certbot renew --cert-name api.acmecorp.example.com
4. Restart nginx to load new cert: systemctl reload nginx
5. Verify: echo | openssl s_client -connect api.acmecorp.example.com:443 2>/dev/null | openssl x509 -noout -dates

SECTION 4: DEPLOYMENT PROCEDURES
====================================================================

All production deployments must be:
1. Approved by at least ONE engineer other than the author (PR review).
2. Deployed during the DEPLOYMENT WINDOW: Tuesday, Wednesday, or Thursday, 10:00–15:00 CT.
   Exception: SEV-1 hotfixes may deploy anytime with SRE Lead approval.
3. Preceded by a staging deployment and smoke test (minimum 30-minute soak).
4. Rolled back within 10 minutes if error rate increases by >5% or P99 latency increases by >50%.

Deployment tool: Argo CD (GitOps). All changes merged to `main` automatically sync to staging. Promotion to production requires manual approval in Argo CD UI.

SECTION 6: BACKUP AND RECOVERY
====================================================================

Database backups:
- Full backup: Daily at 02:00 UTC to S3 bucket acme-prod-backups
- WAL archiving: Continuous to S3 (point-in-time recovery supported)
- Retention: 30 days for daily backups, 7 days for WAL
- Recovery time objective (RTO): 4 hours
- Recovery point objective (RPO): 1 hour

To restore from backup:
1. Identify target backup: aws s3 ls s3://acme-prod-backups/postgres/
2. Provision a new RDS instance from snapshot via Terraform.
3. Replay WAL to desired point: contact DBA on-call.
4. Update DATABASE_URL environment variable in Kubernetes secrets.
5. Restart application pods.

Qdrant snapshots:
- Snapshots created every 6 hours via cron job.
- Stored in /data/qdrant/snapshots/ and synced to S3.
- To restore: curl -X POST http://qdrant:6333/collections/{name}/snapshots/recover
